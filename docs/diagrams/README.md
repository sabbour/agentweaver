# Architecture diagrams

The diagrams embedded as static images in `README.md` ("Block diagram") and
`docs/guide/architecture-aks.md` ("Component diagram", simplified + detailed) are
generated by a small, **generic, data-driven pipeline** — not hand-drawn or
one-off per diagram. GitHub's live Mermaid renderer clips long subgraph/node
labels on diagrams this complex, and pre-rendering to static SVG makes the
result render identically everywhere (GitHub web, VitePress) regardless of
viewer-side renderer quirks.

## How it works

```
docs/diagrams/specs/<name>.json   -- plain node/edge/group graph data (source of truth)
        │
        ▼  npm run docs:render-diagrams
scripts/docs/render-diagrams/     -- ONE generic React Flow + dagre renderer, driven by
                                      Playwright, that works for ANY spec file
        │
        ▼
docs/diagrams/<name>.svg          -- committed, static SVG (what README.md /
                                      architecture-aks.md actually embed)
docs/diagrams/manifest.json       -- SHA-256 hash of each spec, used by the CI drift check
```

There is no per-diagram code. The renderer (`scripts/docs/render-diagrams/src/`) is a
single generic pipeline — the same shared `layoutDiagram()` (dagre auto-layout, including
compound/nested groups) and `buildSvg()` (hand-built, self-contained `<rect>`/`<text>`/
`<path>` SVG, no `foreignObject`) run against whatever spec file it's given. Node/edge
visual style (colors, shapes) matches `apps/web/src/components/WorkflowGraphPanel.tsx`,
the same `@xyflow/react` + `dagre` stack the product uses for its live workflow graphs.

## Adding a new diagram

1. Create `docs/diagrams/specs/<your-diagram-name>.json` with this shape:

   ```jsonc
   {
     "title": "Human-readable title (used as the SVG's <title>)",
     "direction": "TB", // or "LR"
     "groups": [
       // optional — nested clusters/subgraphs. `parent` nests a group inside another group.
       { "id": "azure", "label": "Azure" },
       { "id": "aks", "label": "AKS Cluster", "parent": "azure" }
     ],
     "nodes": [
       // `variant` selects a color category — see NODE_VARIANT_STYLES in
       // scripts/docs/render-diagrams/src/diagramTypes.ts (client/svc/core/
       // workerStyle/runtime/data/ext). `parent` places the node inside a group.
       { "id": "client", "label": "🌐 Client", "variant": "client" },
       { "id": "api", "label": "API ×2", "variant": "core", "parent": "aks" }
     ],
     "edges": [
       // `style` is "solid" (default, arrowed), "dashed" (arrowed, dependency),
       // or "plain" (no arrowhead, shared link).
       { "source": "client", "target": "api", "label": "HTTPS :443" }
     ]
   }
   ```

2. Run `npm run docs:render-diagrams` from the repo root. This discovers every
   `docs/diagrams/specs/*.json` file automatically, renders each to a matching
   `docs/diagrams/<name>.svg`, and updates `docs/diagrams/manifest.json`. **No code
   changes are needed** — the renderer is generic over any spec.
3. Embed the generated SVG wherever you need it, e.g.:
   ```md
   ![Alt text describing the diagram](docs/diagrams/<your-diagram-name>.svg)
   ```
4. Commit the spec JSON, the generated SVG, and the updated `manifest.json` together.

## Editing an existing diagram

Edit its `docs/diagrams/specs/<name>.json`, rerun `npm run docs:render-diagrams`, and
commit the regenerated `.svg` and `manifest.json` alongside the spec change. CI
(`npm run docs:check-diagrams`) fails the build if a spec's content hash doesn't match
what's recorded in the manifest — i.e. if you edit a spec but forget to regenerate/commit
its SVG.

## Why a hash-based drift check, not a pixel/geometry comparison

An earlier version of this pipeline (using `@mermaid-js/mermaid-cli`) checked for drift by
re-rendering and comparing SVG geometry. That broke in CI: headless Chromium's font
metrics differ enough between Windows (dev machines) and Linux (CI runners) that
byte-identical source produced different "golden" geometry per OS. `npm run
docs:check-diagrams` instead compares a normalized (CRLF/LF-independent) SHA-256 hash of
each spec file against `docs/diagrams/manifest.json` — it never re-renders or compares
any rendered output, so it's deterministic and OS-independent by construction.

## First-time setup

`scripts/docs/render-diagrams/` is a standalone package (own `node_modules`, not part of
any npm workspace) using Playwright to drive a headless Chromium instance. `npm run
docs:render-diagrams` installs its dependencies automatically on first run. If Playwright
needs a browser binary installed, run `npx playwright install chromium` from inside
`scripts/docs/render-diagrams/`.
